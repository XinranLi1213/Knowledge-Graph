# 建议评估与数据组合器设计（实施前补充）

日期：2026-10-29。本文件评估本次建议并确定后续实施约束；不实现前端DataStore或API调用。

## 1. 逐项结论

| 建议 | 结论 | 本项目的采用方式 |
|---|---|---|
| DataStore只读合并 | 采用 | 按node_id关联公共结构、当前快照与当前角色建议，生成新的展示投影，不修改源数据 |
| D3完全不用改、坐标绝对不乱跳 | 不能原样承诺 | 保留力导向算法；必须调整现有初始化、节点状态读取与布局对象生命周期 |
| stroke_style隔离业务判定 | 采用 | 属于派生展示字段，不进入客观评价快照，不允许LLM写入 |
| 一阶邻域裁剪 | 局部诊断采用，总体画像另设模式 | 节点诊断按真实边取一阶；总体画像用能力摘要与少量重点证据 |
| 强制JSON Schema输出 | 采用，但需提供方/端点适配 | 业务Schema不能直接整份发送；仍需完整业务校验和异常处理 |
| 候选差异预览、教师采纳后发布 | 采用，留在LLM后续阶段 | 候选独立保存，确认后版本检查并原子发布，不直接修改候选对象充当持久化 |

## 2. DataStore职责与只读投影

DataStore可以作为前端模块中的一个类实现，但类名不是功能要求。它负责加载/缓存、版本核对、关联和当前展示对象的原子切换，不负责成绩计算、身份认证或调用LLM。

“4个文件”指4类核心数据：公共图谱、名册、对象快照、建议包。实际还有manifest、评价策略和资源目录。不能每次切换学生都重新fetch全部文件。

| 数据 | 缓存键 | 切换时行为 |
|---|---|---|
| 公共图谱 | graph_id + graph_version | 首次加载，结构版本不变则复用 |
| 名册 | registry_version | 身份选择器复用 |
| 策略、资源 | policy_id/version、catalog_version | 复用，版本改变才重取 |
| 评价快照 | subject.type/id + snapshot_id/revision | 按当前对象与场景加载/复用 |
| 建议包 | subject + bundle_id/version | 加载完整包，按audience筛选后投影；教师/学生不能共用已筛选缓存 |

文件路径由manifest解析；路径中的名字不是可信版本号。成功加载后检查graph_ref、subject、snapshot revision、profile_version、资源版本和角色，再一次性切换当前投影。用请求序号或AbortController丢弃旧请求；取消旧请求之外，仍要检查请求序号，避免已缓存结果或已完成请求串入。

展示节点的设计示例（仅结构示意，不是新的持久化成绩契约）：

```text
ViewNode {
  id, level, label, display_weight, ...公共属性,
  status: 当前对象节点结果的只读副本,
  sidebar_info: {
    description,
    display_score, score_label,
    assessment_sources,
    recommendations: 当前角色该节点的active建议数组
  },
  presentation: { fill, stroke_style, badges }
}
```

总体建议target_node_id=null，放在独立overview中，不能重复挂到每个节点上。按node_id建立建议数组索引，保留一节点多建议能力，不用find只取第一条。

缺少结果时构造明确的空展示状态，缺少建议时显示暂无建议；不回退到班均、不借用其他角色、不沿用上一人的数据。个人分数不写进旧average_score字段。开发测试中可冻结原始对象以发现误写，生产环境以清晰的所有权和只读接口为主。

## 3. 为什么不能保证D3完全不改

现有src/app.js的load()每次都会调用setupLayout()；setupLayout()会重新创建layouts和simulation。现有layouts还将业务节点展开复制到物理节点中，因此新投影不会自动更新旧布局对象里的status。只替换data.nodes并不足以更新颜色，也不能阻止重新布局。

后续必须分离：

```text
immutable source data → DataStore → ViewNode / overview
graph_ref → LayoutStore → id, x, y, vx, vy, fx, fy, radius
ViewNode + LayoutStore → SVG属性与侧栏
```

同一图谱版本只建立一份布局。D3 forceSimulation会修改传入的物理节点，forceLink也会维护自己的端点引用，所以要给D3单独的可变节点和边副本，不能把冻结的公共节点或展示投影直接交给力模拟。[D3官方说明](https://d3js.org/d3-force/simulation)

保留.data(..., n => n.id)的稳定关联。切学生、角色、场景或建议版本时，只刷新属性和侧栏：不得重新setupLayout、simulation.nodes、设置alpha/restart、清空SVG、自动fit或重置缩放。渲染时从当前viewById读取状态，不从旧布局副本读取。

“坐标稳定”的验收范围是：同一graph_ref、相同视口、模拟已经稳定且没有拖动时，切换对象前后各节点x/y/fx/fy与缩放变换一致。物理模拟仍在运行时保持连续运动，不人为重置。用户拖动、主动适应画布、结构版本更新和视口调整不属于绝对不动的承诺。

## 4. stroke_style的归属与优先级

由单独presentation mapper产生fill与stroke_style，SVG只映射这些属性，不在绘图回调中重复判断学习状态。

诊断模式阶段低分条件：health_color=grey、score_is_provisional=true、得分为有限数字且低于当前策略yellow_min。0分有效，null不是0；不重新聚合成绩或推算coverage。结构模式继续按层级着色。

```text
presentation.stroke_style = {
  color: "#df743e",
  width: 3,
  dasharray: "5 3"
}
```

这只是派生展示数据，存储依据仍是status与policy。不得把stroke_style写入学生快照、公共图谱或recommendation_update。

灰色未开始、无证据、覆盖不足仍用标签区分。阶段低分描边与选中高亮分成不同SVG元素：风险描边保留，选中时另画外环，避免.selected覆盖橙色描边。键盘聚焦、hover也不应遮掉风险提示。

## 5. 一阶上下文不是全文递归

局部诊断以目标节点为中心，只纳入图谱中真实相连的一阶节点及连接边。C05的一阶包括6个知识点、直接支撑能力、C02模拟电子技术和C14射频电路设计。当前没有C04信号与系统→C05的直接先修边，不能用自然语言常识补造。

一阶关系按类型解释：上层能力提供支撑背景，先修用于学习基础，后继用于提醒；相似/并列不传成绩。邻居节点的邻居不再默认扩张。

能力和课程的已有分数可以作为快照事实摘要，但不为补齐其全部聚合证据而递归拉取所有其他课程。输入明确标注省略证据和省略聚合输入的数量，模型不得据摘要推断外围知识点成绩。需要进一步解释时发起另一个明确目标请求，而非悄悄扩张上下文。

总体画像采用overview_summary：12项能力及其覆盖率、少量已评价强弱项/阶段性低分、对应课程与有限证据。不强行从单个C05邻域生成整个学生画像，也不把完整大纲发给模型。局部请求和总体请求使用不同context_id与可写目标范围。

## 6. Structured Outputs与候选预览

优先用端点原生JSON Schema约束，不正则截取自由文本。保留业务Schema与API兼容Schema两层：根对象、upsert/remove分支和受支持关键字由提供方适配；完整业务边界在本系统继续校验。不同端点配置和异常处理见LLM建议读写协议.md。

未来教师侧栏按recommendation_id比较原active建议与候选建议，展示新增、修改、删除，以及依据和资源的变化。候选只投影到独立预览层，不替换当前active缓存，不改节点成绩、health_color或stroke_style。学生默认只能看到已发布建议。

“确认采纳”是发布命令，不是客户端把candidate字符串改成active。未来服务端须重新核对对象、角色、快照和各版本，执行全部操作并持久化新bundle版本，记录操作者、update_id、时间和依据；失败则active不变。一个bundle中教师与学生建议共用版本，任一角色先发布后，其他旧候选都必须重新校验/生成。

展示角色audience不等于审核者身份：教师可以审核面向学生的建议。真实发布权限属于后续后端阶段；本次模拟角色选择不构成身份认证。
